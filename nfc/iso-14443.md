# ISO/IEC 14443

**Full title:** *Identification cards - Contactless integrated circuit cards - Proximity cards*

ISO 14443 defines **how a card and a reader talk to each other over a few centimeters of air**. It is the plumbing under almost every tap-to-pay card, transit card, hotel key, office badge, and e-passport, plus the "tap your phone" mode of NFC.

In one sentence: *it defines a 13.56 MHz radio link where the reader powers the card wirelessly, picks exactly one card out of several in the field, and then provides a reliable byte pipe.* It deliberately says nothing about what those bytes mean - that is [ISO 7816](iso-7816.md)'s job.

## The mental model: a wireless power socket that also carries data

A contactless card has no battery. This single fact drives the entire design.

The reader continuously radiates a 13.56 MHz magnetic field. The card has a coil printed around the edge of the plastic, and the field induces a current in it that powers the chip. This is a transformer whose two halves are separated by air, which is why it is called **inductive coupling**.

```
        READER (PCD)                        CARD (PICC)
   ┌─────────────────┐              ┌────────────────────┐
   │  13.56 MHz osc  │  ))))))))))  │   antenna coil     │
   │        │        │   magnetic   │        │           │
   │   ┌────┴────┐   │    field     │   ┌────┴─────┐     │
   │   │ antenna │───┼── ~0-4 cm ───┼──>│ rectifier│     │
   │   │  coil   │   │              │   └────┬─────┘     │
   │   └────┬────┘   │              │        │ power     │
   │   ┌────┴────┐   │              │   ┌────┴─────┐     │
   │   │ demod   │<──┼── load mod ──┼───│   chip   │     │
   │   └─────────┘   │              │   └──────────┘     │
   └─────────────────┘              └────────────────────┘
      powered, active                  passive, parasitic
```

The card has no transmitter, so it cannot shout back. It replies by **load modulation**: switching a resistor across its own coil, which is reflected into the reader's coil as a tiny voltage change. The card is not sending a signal so much as deliberately disturbing the reader's own signal.

Two consequences explain most of the standard's quirks:

- **The reader is always the master.** The card never speaks first, never interrupts, and never times out on its own. Every exchange is strictly request-then-response, half duplex. If the card needs more time it has to formally *ask* for an extension.
- **Range is tiny and non-negotiable.** Inductive coupling falls off steeply, giving a working range of **0 to about 4 cm**. This is a feature: it makes "tap the thing you intended to tap" a meaningful gesture and makes remote skimming hard.

Two terms appear everywhere, including in error messages:

- **PCD** - Proximity Coupling Device, i.e. the reader.
- **PICC** - Proximity Integrated Circuit Card, i.e. the card, tag, or phone in card mode.

## The four parts

ISO 14443 is four documents that stack. This diagram tells you which one to go read when something breaks:

```
  ┌────────────────────────────────────────────────────────┐
  │  Application: EMV payment, ePassport, transit, NDEF...  │ <- not in
  ├────────────────────────────────────────────────────────┤    14443
  │  ISO 7816-4 APDUs (command/response messages)          │
  ╞════════════════════════════════════════════════════════╡
  │  Part 4: Transmission protocol                         │
  │    reliable byte pipe. Blocks, ACK/NAK, chaining.      │
  ├────────────────────────────────────────────────────────┤
  │  Part 3: Initialization and anticollision              │
  │    pick exactly one card, learn its UID, activate it.  │
  ├────────────────────────────────────────────────────────┤
  │  Part 2: RF power and signal interface                 │
  │    13.56 MHz, how a 1 and a 0 look on the air.         │
  │    Type A and Type B differ here.                      │
  ├────────────────────────────────────────────────────────┤
  │  Part 1: Physical characteristics                      │
  │    card size and durability.                           │
  └────────────────────────────────────────────────────────┘
```

Read it bottom-up as a boot sequence: the card gets powered (1, 2), gets singled out and named (3), gets a reliable channel (4), and then real work happens in a layer the standard does not define.

### Part 1 - Physical characteristics

A proximity card is an **ID-1** card, 85.6 x 54 mm, the outline of a credit card, and it specifies the bending, heat, and UV abuse it must survive. Note that Part 1 does not require the card to be a card: key fobs, stickers, passport inlays, and phones all speak ISO 14443 while ignoring Part 1 entirely.

### Part 2 - How a 1 and a 0 look on the air

This is where **Type A and Type B** differ, and it is the only place they meaningfully differ. Both run at 13.56 MHz and both use load modulation for the reply; they made opposite choices about how deeply the reader modulates its carrier.

- **Type A** (NXP/MIFARE lineage, by far the most common) uses **100% ASK** reader-to-card: the carrier switches off briefly to create "pauses", and the pause position encodes the bit. Because the field drops to zero, the card is momentarily unpowered and rides through on an onboard capacitor.
- **Type B** (banking cards, many national IDs) uses **10% ASK**: the carrier only dips slightly, so the card is never starved of power, and a simple high/low level carries the bit.

The **base bit rate is 106 kbit/s** (`fc/128`). 212, 424, and 848 kbit/s are optional and negotiated after activation, so every conversation *starts* at 106.

A reader must poll for both types alternately, since it cannot know which will appear. The two are mutually unintelligible here but converge again at Part 4, after which an application usually cannot tell which it is using and should not care.

Do not confuse these with Sony's FeliCa, which is a separate standard (JIS X 6319-4). The NFC Forum calls Type A **NFC-A**, Type B **NFC-B**, and FeliCa **NFC-F**.

### Part 3 - Anticollision: picking one card out of many

The interesting part, and the one that explains real-world weirdness like "why does my badge fail when it shares a wallet with my transit card?"

Several cards may be in the field at once. They are all powered, all listening, and all mute until spoken to. If the reader says "identify yourself" they answer simultaneously and their load modulations overlap into garbage. The reader needs to isolate exactly one.

Every card runs a small state machine:

```
                power up in field
                        │
                        v
   ┌──────────┐  REQA/WUPA   ┌──────────┐   SELECT   ┌──────────┐
   │   IDLE   │ ───────────> │  READY   │ ─────────> │  ACTIVE  │
   │          │              │ (anti-   │            │ (talking)│
   │          │              │ collision│            │          │
   └──────────┘              │  loop)   │            └────┬─────┘
        ^                    └──────────┘                 │ HLTA
        │                                                 v
        │                                            ┌──────────┐
        └──────── leave field ───────────────────────│   HALT   │
                                                     │ (ignores │
                  WUPA only ─────────────────────────> │  REQA) │
                                                     └──────────┘
```

`HALT` is the clever bit. Once the reader finishes with a card it tells it to halt, and a halted card ignores the normal "anyone there?" poll (`REQA`). That lets the reader work through a stack of cards one at a time without already-handled ones answering again. Only the stronger `WUPA` wakes a halted card.

#### The anticollision loop (Type A)

The reader performs a **bitwise binary search over UIDs**. It works because of a property of the card's Manchester coding: when two cards send different bits in the same bit period, the reader does not see corrupted mush, it sees an *illegal* symbol. So it detects not just that a collision happened but **exactly which bit position collided**.

1. Reader broadcasts `REQA`. Every idle card answers, revealing that somebody is there and how long its UID is.
2. Reader asks for UIDs, prefixed with the bits it already knows (initially none).
3. Every card matching that prefix replies with the rest of its UID.
4. The reader spots the first collided bit, picks `0` or `1` arbitrarily, and loops with one more known bit.
5. When a round completes with no collision, the reader has a full UID. It sends `SELECT` with it; the matching card goes `ACTIVE` and the rest stand down.

```
  Card X UID bits: 1 0 1 1 0 1 ...
  Card Y UID bits: 1 0 1 0 1 1 ...
                         ^ first difference, bit 4

  Round 1  reader knows nothing; both cards reply
           reader sees:  1 0 1 X ...      X = collision at bit 4
           reader picks 0

  Round 2  reader sends "I know 1 0 1 0"
           only Card Y matches and replies with the rest
           reader sees:  1 0 1 0 1 1 ...  no collision -> full UID
           reader SELECTs Card Y, does its business, HALTs it

  Round 3  reader sends REQA again
           Card Y is halted and silent; only Card X answers
           reader gets Card X's UID with no collisions at all
```

This always terminates and always enumerates every card, which is why it is called *deterministic* anticollision. Type B instead uses a probabilistic, slotted-ALOHA scheme: cards pick a random slot out of N and the reader retries collided slots. Simpler in silicon, but with no hard upper bound on time.

A UID is 4, 7, or 10 bytes. Since one round only carries 4 bytes, longer UIDs are fetched over two or three **cascade levels**.

#### The one bit that matters most

The reply to a successful `SELECT` is a byte called **`SAK`**, and **bit 6 is the fork in the road for the entire stack**:

- **Set** - the card supports ISO 14443-4. The reader proceeds to get a real transport protocol, and almost certainly [ISO 7816-4](iso-7816.md) APDUs on top.
- **Clear** - the card implements Part 3 only, and anything above it is proprietary.

**MIFARE Classic is the famous example of the second case**: standard 14443-3 anticollision, then NXP's proprietary Crypto1 and a bespoke command set. This is why a MIFARE Classic tag and a bank card look identical for the first few milliseconds and then diverge completely. It is also exactly the NFC Forum's Type 2 versus Type 4 tag distinction.

### Part 4 - The transport protocol

By now the reader has one card activated and can exchange raw frames. Part 4 turns that into something recognizable as a **connection**: reliable, ordered, half duplex, able to carry messages larger than one frame and to recover from errors.

It opens with a capability handshake (`RATS`/`ATS` on Type A) that negotiates bit rate and, importantly, **maximum frame size - capped at 256 bytes**. It also sets the **Frame Waiting Time**, the deadline by which the card must start replying, defaulting to about 4.8 ms.

After that, everything is a **block** with a one-byte control header:

```
  ┌─────┬───────┬───────┬──────────────────┬─────────┐
  │ PCB │ [CID] │ [NAD] │      INF         │   EDC   │
  └─────┴───────┴───────┴──────────────────┴─────────┘
    1 B    opt     opt         payload        CRC, 2 B

  I-block   carries data. Has an alternating block number so
            duplicates can be spotted, and a chaining bit.
  R-block   no data, just ACK or NAK.
  S-block   supervisory:
              S(WTX)      card: "I need more time"
              S(DESELECT) reader: "we are done, go to HALT"
```

Two mechanisms here show up as real observable behaviour:

- **Chaining.** A 2 KB message cannot fit in a 256-byte frame, so it is split and every segment but the last sets the chaining bit, each acknowledged separately. This is why a large read over NFC is many round trips.
- **Waiting time extension.** If the card needs 200 ms for an RSA signature but the deadline is 4.8 ms, it would time out. Instead it replies `S(WTX)` to buy time and the clock restarts. When a contactless payment "hangs" for a beat, this is often what is happening: the card is repeatedly asking for extensions while doing asymmetric crypto on a chip powered by a magnetic field.

## Where ISO 14443 sits in the wider NFC world

"NFC" is an umbrella over several standards, and ISO 14443 is only one:

```
  NFC Forum name   Underlying standard      Typical use
  ──────────────   ─────────────────────    ────────────────────────
  NFC-A            ISO 14443 Type A         MIFARE, most tags,
                                            bank cards, badges
  NFC-B            ISO 14443 Type B         banking, national ID,
                                            ePassports
  NFC-F            JIS X 6319-4 (FeliCa)    Japan: Suica, Edy
  NFC-V            ISO 15693                "vicinity" cards, ~1 m
  peer-to-peer     ISO 18092 / NFCIP-1      phone-to-phone (largely
                                            abandoned in practice)
```

When your phone acts as a card (Apple Pay, Google Wallet, a badge in your wallet app) it is doing **ISO 14443 card emulation** - deliberately pretending to be a PICC, right down to running the anticollision loop. When it reads a tag it acts as a PCD.

## Security: what the standard does and does not give you

**ISO 14443 provides no confidentiality, no integrity against an active attacker, and no authentication.** The CRC and parity bits catch *accidental* bit errors from a noisy coupling, not deliberate tampering. Everything security-relevant happens above: EMV cryptograms, ePassport BAC/PACE, [secure messaging](iso-7816.md#secure-messaging), or a proprietary scheme.

The attacks follow directly from the physics:

- **Eavesdropping.** It is radio. An attacker only needs to *hear* the field, not power a chip from it, so reader-to-card traffic can be captured well beyond the operating range - demonstrated from tens of centimeters to a few meters with a good antenna.
- **Relay / man-in-the-middle.** The card answers anyone who powers it, so an attacker can put a proxy near the victim's card and a clone near the real reader and tunnel frames over the internet, bypassing the short range entirely. The only robust defense is timing-based distance bounding, which the base standard does not provide; EMV added a relay-resistance protocol for exactly this.
- **Tracking.** A fixed UID is a stable identifier broadcast to any reader. Hence the standard permits **random UIDs** regenerated per activation, which phones in card-emulation mode almost always use.

The practical takeaway: **treat the link as an open, untrusted channel that anyone can read and replay**, exactly as you would treat plain HTTP over public wifi.

## Common gotchas

- **Two cards in one wallet.** Anticollision handles this at the protocol level, but many readers deliberately bail out on detecting more than one card, since they cannot know which you meant. Separately, two stacked coils detune each other and steal each other's power, so sometimes neither card boots. Both failures look identical to the user.
- **Metal kills it.** A conductive surface behind the card absorbs the field via eddy currents. This is what the ferrite shielding layers in phones and tags are for.
- **"MIFARE" is not a standard**, it is a product family. MIFARE Classic's crypto has been thoroughly broken since 2008 and should be treated as offering no security; DESFire EV2/EV3 are full 14443-4 cards with real AES. "We use MIFARE" conveys nothing about your security posture.
- **The card can drop out mid-transaction.** The user's hand moves, the field is lost, and the chip dies instantly with no chance to clean up. Any state change on the card must be **atomic and idempotent**.
- **106 kbit/s is slow.** After framing, parity, CRC, and turnaround gaps, real throughput is in the low tens of kbit/s. Combined with 256-byte frames and chaining, reading a passport photo takes seconds. Move as few bytes as possible.
