# ISO/IEC 7816

**Full title:** *Identification cards - Integrated circuit cards*

If [ISO 14443](iso-14443.md) is the wireless pipe, **ISO 7816 is the language you speak down the pipe**. It defines what a smart card is from a software point of view: a tiny server with a file system, a command set, an access control model, and a set of status codes.

In one sentence: *it defines a request/response protocol called APDUs, plus a hierarchical file system and security model that those APDUs operate on.* It was written for cards with gold contacts, but its most important part turned out to be transport-independent, so it now runs over contactless links too.

## The mental model: the card is an HTTP server

The most useful analogy: **a smart card is a request/response server, and APDUs are its HTTP.**

```
   Terminal (client)                          Card (server)
   ─────────────────                          ─────────────
   "SELECT the payment app"      ──────>
                                 <──────      "OK, 9000"
   "READ 16 bytes from file 2"   ──────>
                                 <──────      "here they are, 9000"
   "VERIFY this PIN"             ──────>
                                 <──────      "wrong, 63C2 (2 tries left)"
   "READ the private file"       ──────>
                                 <──────      "6982, not authenticated"
```

Every property you would expect of that analogy holds:

- The terminal always initiates; the card never speaks unprompted.
- There is a **session**: what you can do depends on what you have already done. Selecting an application and verifying a PIN change the card's state, and that state dies when power is removed.
- There are **resources** in a path-like hierarchy, and methods to read and write them.
- There are **status codes** in families, where `9000` is `200 OK`, `6982` is `401 Unauthorized`, and `6A82` is `404 Not Found`.

Where it breaks down: the card has kilobytes of memory, a single-digit-megahertz clock, no ability to retry on its own, and can lose power at any instant when the user's hand moves.

## The parts, and the one that matters

ISO 7816 is a large multi-part standard, but for practical purposes there are only two parts, and really only one:

- **Part 3 - Electrical interface and transmission protocols.** `ATR`, `T=0`, `T=1`. **Contact cards only.**
- **Part 4 - Organization, security and commands for interchange.** APDUs, the file system, security. **This is the one.**

The rest cover card dimensions and contact layout (1, 2), AID registration (5), standard data elements (6), security operations and file management commands (8, 9), and various niches.

The crucial architectural point:

```
           CONTACT CARD                      CONTACTLESS CARD
        ┌─────────────────┐                ┌─────────────────┐
        │   Application   │                │   Application   │
        ├─────────────────┤                ├─────────────────┤
        │  ISO 7816-4     │  <-- SAME -->  │   ISO 7816-4    │
        │  APDUs + files  │                │   APDUs + files │
        ├─────────────────┤                ├─────────────────┤
        │  ISO 7816-3     │                │  ISO 14443-4    │
        │  T=0 or T=1     │                │  block protocol │
        ├─────────────────┤                ├─────────────────┤
        │  ISO 7816-1/2   │                │  ISO 14443-1/2/3│
        │  gold contacts  │                │  13.56 MHz radio│
        └─────────────────┘                └─────────────────┘
```

**Part 4 is identical on both sides.** A dual-interface bank card runs one piece of application software that does not know whether the APDU arrived over metal contacts or a magnetic field. So an NFC developer can skip Part 3 almost entirely.

Almost. Part 3's `T=0` protocol has a structural quirk that leaks upward: a single exchange can carry data *either* to the card *or* from it, never both. Commands that need both ("here is a challenge, return the signature") are worked around by the card replying **`61 XX`** - "I am done and `XX` bytes are waiting" - after which the terminal issues a separate **`GET RESPONSE`** to collect them. This is pure contact-card plumbing and unnecessary over contactless, **but you will still have to handle it**, because card OSes and application specs were all written against `T=0` habits. Budget for it.

## Part 4, level 1: the APDU

This is the core of everything. **APDU** = Application Protocol Data Unit, one in each direction.

```
  COMMAND APDU
  ┌─────┬─────┬─────┬─────┬─────┬──────────────┬─────┐
  │ CLA │ INS │ P1  │ P2  │ Lc  │     Data     │ Le  │
  └─────┴─────┴─────┴─────┴─────┴──────────────┴─────┘
   └───── header, always 4 bytes ────┘
                                └──── body, all optional ────┘

  CLA  class        command family, plus flags: secure messaging
                    on/off, which logical channel
  INS  instruction  the verb: SELECT, READ BINARY, VERIFY...
  P1   parameter 1  meaning depends entirely on INS
  P2   parameter 2  likewise
  Lc   how many bytes of Data I am sending
  Le   how many bytes I want back

  RESPONSE APDU
  ┌──────────────────┬─────┬─────┐
  │       Data       │ SW1 │ SW2 │
  └──────────────────┴─────┴─────┘
      optional         the status word, ALWAYS present
```

Because `Lc`, `Data`, and `Le` are each optional, commands come in exactly four shapes. Card documentation says "this is a Case 4 command" and expects you to know:

```
  Case 1   CLA INS P1 P2                  no data either way
  Case 2   CLA INS P1 P2 Le               data comes back only   (READ)
  Case 3   CLA INS P1 P2 Lc Data          data goes in only      (VERIFY)
  Case 4   CLA INS P1 P2 Lc Data Le       both ways              (AUTH)
```

In the basic encoding `Lc` and `Le` are one byte, so at most 255 bytes in and 256 out - with the deliberate special case that **`Le = 0x00` means 256**, not zero. Optional *extended length* encoding raises this to 65535/65536, which saves APDU round trips but not radio traffic, since ISO 14443 frames still cap at 256 bytes underneath.

### CLA is a bitfield, not an opaque number

The values you see in the wild look arbitrary but are not:

```
  bit  8 7 6 5 4 3 2 1
       │ │ │ │ │ │ └─┴── logical channel number, 0-3
       │ │ │ │ └─┴────── secure messaging: 00 = none,
       │ │ │ │            0C = SM with the header authenticated
       │ └─┴─┴────────── command chaining, channel extension
       └──────────────── 0 = interindustry (ISO-defined)
                         1 = proprietary (vendor's own command set)
```

In practice:

- **`0x00`** - standard ISO command, channel 0, no secure messaging. The common case.
- **`0x0C`** - same command wrapped in secure messaging. Once an ePassport or GlobalPlatform card establishes a session, every APDU flips to this.
- **`0x80`, `0x90`** - proprietary. Seeing `0x80` tells you the ISO spec will *not* explain this command and you need the vendor's document.

### The commands you will actually use

| INS | Name | What it does |
|---|---|---|
| `A4` | `SELECT` | choose a file or application - the "cd" of smart cards |
| `B0` | `READ BINARY` | read bytes at an offset |
| `D6` | `UPDATE BINARY` | write bytes at an offset |
| `B2` | `READ RECORD` | read record N from a record-structured file |
| `CA` | `GET DATA` | read a data object by tag, no file needed |
| `20` | `VERIFY` | present a PIN |
| `84` | `GET CHALLENGE` | ask the card for a random nonce |
| `82` | `EXTERNAL AUTHENTICATE` | prove the *terminal* knows a key |
| `88` | `INTERNAL AUTHENTICATE` | make the *card* prove it knows a key |
| `C0` | `GET RESPONSE` | collect data after a `61 XX` |

`SELECT` deserves detail, because `P1` picks the *addressing mode* and this is where most beginner bugs live:

```
  P1 = 00   by file identifier (2 bytes in Data), or the MF if empty
  P1 = 02   select an EF under the current DF
  P1 = 03   select the parent DF ("cd ..")
  P1 = 04   BY NAME - Data is an AID. This is how you pick an application.
  P1 = 08   by absolute path from the root

  P2 = 00   return the full file control information
  P2 = 0C   return nothing, just do it   <- common, saves bytes
```

A complete exchange, selecting the NDEF application on an NFC Forum Type 4 tag:

```
  ->  00 A4 04 00 07 D2760000850101 00
      │  │  │  │  │  └─ the AID    └─ Le = 0, "send back up to 256"
      │  │  │  │  └─ Lc = 7 bytes of AID follow
      │  │  │  └─ P2 = 00
      │  │  └─ P1 = 04, select by name
      │  └─ INS = A4, SELECT
      └─ CLA = 00, interindustry, no SM, channel 0

  <-  90 00
```

## Part 4, level 2: the file system

A card's storage is a tree, and the naming is unfortunate but universal:

```
                    MF  (Master File, ID 3F00)
                     │     the root directory. Always exists.
        ┌────────────┼────────────────┐
        │            │                │
       DF           DF               EF
   (Dedicated    (Dedicated      (Elementary
     File)          File)           File)
   = a directory / application    = a file with bytes in it
        │
   ┌────┴────┐
  EF        EF
```

- **MF** - the root, always file identifier `3F00`.
- **DF** - Dedicated File. Despite the name, this is a **directory**. One that represents a self-contained application is also called an ADF.
- **EF** - Elementary File. This is a **file**, holding the actual data.

Every file has a 2-byte identifier and optionally a 5-bit **Short File Identifier (SFI)**. The SFI is a bandwidth optimization: rather than `SELECT` then `READ` (two round trips), you name the SFI inside the read command and do it in one. On a slow contactless link that halves your traffic, so real specs like EMV use SFIs heavily.

EFs come in four structures, and the choice is a real design decision:

- **Transparent** - a flat byte array addressed by offset. For certificates, photos, NDEF, anything variable-shaped.
- **Linear fixed** - N equal-size records addressed by number.
- **Linear variable** - N records of individual lengths.
- **Cyclic** - fixed records in a ring, where writing past the end overwrites the oldest. A small piece of elegance: "keep the last N transactions" is implemented once, in the card OS, with power-loss atomicity handled for you.

Applications are named globally rather than by path, using an **AID** of up to 16 bytes: a 5-byte registered provider ID plus an extension the provider subdivides freely. The first nibble says which registry - `A` international, `D` national, `F` private/unregistered. `F...` is the `192.168.0.0/16` of smart cards; use it for internal projects rather than squatting on someone's registered prefix.

```
  D2760000850101           NFC Forum NDEF Tag Application
  A0000000031010           Visa credit/debit
  A0000002471001           ICAO ePassport
```

### Reading a Type 4 tag, end to end

This ties the whole stack together, and is the most common real use of ISO 7816-4 over ISO 14443:

```
  ISO 14443-3  REQA / anticollision / SELECT  -> UID, SAK bit 6 set
  ISO 14443-4  RATS                           -> transport ready
  ────────────────────────── now ISO 7816-4 ──────────────────────────

  1. Select the NDEF application by AID
     ->  00 A4 04 00 07 D2760000850101 00
     <-  90 00

  2. Select the Capability Container file
     ->  00 A4 00 0C 02 E103
     <-  90 00

  3. Read the CC: it gives max APDU sizes, the NDEF file's ID,
     its max length, and read/write permissions
     ->  00 B0 0000 0F
     <-  000F20003B00340406E10400FF0000 9000
                            └─ NDEF file is E104

  4. Select the NDEF file
     ->  00 A4 00 0C 02 E104
     <-  90 00

  5. Read the 2-byte length prefix
     ->  00 B0 0000 02
     <-  0021 9000        -> 0x21 = 33 bytes of NDEF follow

  6. Read the message itself, from offset 2
     ->  00 B0 0002 21
     <-  D1012E5504... 9000
```

Notice the shape: **six round trips and two indirections just to learn how long the payload is.** Over a 106 kbit/s link this is why tag reads feel deliberate rather than instant, and why SFIs exist.

## Part 4, level 3: security

ISO 7816-4 does not just store files, it guards them.

**Access conditions.** Every file carries rules in its control information, per operation, expressed as a condition that must be satisfied first: always, never, PIN verified, authenticated with key K, or combinations. **The card OS enforces this, not the application.** `69 82` is what refused you. The architectural point is that **the terminal is not trusted** - a hostile terminal can send any APDU it likes and will simply be told no. That is the entire reason smart cards exist instead of memory cards.

**Authentication**, in three commands where direction is everything:

- `GET CHALLENGE` - the card supplies a random nonce. Nonces come from whoever wants freshness.
- `EXTERNAL AUTHENTICATE` - the *terminal* proves it holds a key, unlocking privileged operations.
- `INTERNAL AUTHENTICATE` - the *card* proves it holds a key. This is how you detect a cloned card.

Run both ways with session key derivation, this becomes mutual authentication and yields keys for secure messaging. That is the basis of GlobalPlatform SCP02/SCP03, ePassport BAC, and DESFire AES.

### Secure messaging

Once keys exist, individual APDUs can be wrapped so the link no longer has to be trusted. Recall that [ISO 14443 provides no security at all](iso-14443.md#security-what-the-standard-does-and-does-not-give-you) - this is the layer that fixes it.

Set `CLA` bit 4 (so `00` becomes `0C`) and replace the plain body with TLV-encoded objects:

```
  Plain:    00 B0 0000 0F                      read 15 bytes at offset 0

  Wrapped:  0C B0 0000 19 [97 01 0F] [8E 08 <8-byte MAC>] 00
            │              │          └─ 8E: MAC over the header
            │              │             AND all the objects
            │              └─ 97: the original Le, now authenticated
            └─ CLA bit 4: secure messaging, header authenticated

  Other common tags:  87 encrypted data   99 protected status word
```

Two properties are easy to overlook. The **header is authenticated**, so an attacker cannot rewrite `READ` into `UPDATE` or change the offset. And the **response status word is protected too** (tag `99`), so an attacker cannot forge a `90 00` success or downgrade an error - a subtlety that has produced real vulnerabilities in implementations that MACed the data but not the status.

## Status words: the error taxonomy

Learn these as families rather than individually.

```
  90 00     success

  61 XX     success, XX bytes waiting -> send GET RESPONSE
  6C XX     wrong Le; XX is the correct value -> resend with Le = XX

  63 00     verification failed
  63 CX     verification failed, X retries remaining     <- read X!

  67 00     wrong length
  69 82     security status not satisfied                <- "401"
  69 83     authentication method blocked                <- PIN exhausted
  69 85     conditions of use not satisfied              <- wrong order
  6A 82     file or application not found                <- "404"
  6A 86     incorrect P1-P2
  6B 00     wrong parameters (offset beyond end of file)
  6D 00     INS not supported             <- wrong app selected?
  6E 00     CLA not supported             <- proprietary vs 00 mixup
  6F 00     no precise diagnosis          <- the card gave up
```

Debugging heuristics that follow:

- **`6D 00` / `6E 00`** almost always means you are talking to the wrong *thing*, not that your command is malformed. You forgot to `SELECT`, or you sent `CLA=00` to a proprietary applet.
- **`63 CX`** - always parse out `X`. A PIN with three tries is one mistake from `69 83`, which on most cards is **permanent**. Never brute-force a PIN against a card you care about.
- **`69 85`** means right command, wrong moment: you skipped a prerequisite.
- **`6C XX` is a gift, not an error.** The card is telling you the exact correct length. Resend with `Le = XX`.
- **`6F 00`** is the card's shrug - usually a field drop mid-command or a broken applet.

## Practical notes

- **The card can lose power at any instant.** On contactless this is routine, not exceptional. Any multi-APDU operation must be safe to restart from the beginning, and writes must be atomic. Card OSes provide transaction primitives; use them.
- **Round trips are the dominant cost.** Each exchange costs milliseconds, and anything over 256 bytes gets chained underneath. Use SFIs, use `P2=0C` to suppress information you will not read, and count round trips as carefully as you would count SQL queries in a web request.
- **Everything is big-endian hex.** `P1 P2 = 00 10` is offset 16, not 4096.
- **Test against a card you can afford to brick.** Wrong keys and exhausted PIN counters cause permanent lockout by design.
- **Nobody implements bare 7816-4 in production.** You implement EMV Book 3, ICAO 9303, NIST SP 800-73 (PIV), or the NFC Forum Type 4 Tag spec, each of which pins down which files exist, which AID to select, and what the data means. Those documents are far more concrete than the ISO text. Read the profile and use ISO 7816-4 as the reference for the grammar.

## Where you will meet this

EMV contactless payment, ePassports (ICAO 9303, with `EF.DG1..DG16` and BAC/PACE secure messaging), NFC Forum Type 4 tags, SIM/USIM cards (over contacts with `T=0`), PIV and CAC government IDs, Java Card applets addressed by AID, and MIFARE DESFire in its ISO-wrapped mode.
